# Problem: EVM is scattered across speculative and duplicated layers

Status: architecture investigation and refactor charter for `refac-evm`.

This document describes the current problem, the code that should be deleted or consolidated, the
minimum architecture that should replace it, and a buildable commit sequence. It is intentionally
deletion-oriented. It does not preserve current crates, public types, schema ids, config shapes,
entry points, persisted runs, or internal extension points merely because they already exist. Git
history is the recovery mechanism for removed code.

The governing optimization order is:

1. fewer concepts;
2. fewer execution and replay paths;
3. fewer public types and schemas;
4. fewer duplicated responsibilities;
5. fewer files and crates that a future EVM change must touch;
6. less code, once the correctness and security invariants are satisfied.

There is no backward-compatibility requirement. The implementation must not add deprecated aliases,
old-schema readers, migration facades, fallback parsers, parallel implementations, or re-export
shims. A replacement commit deletes the superseded path in that same commit.

## Executive finding

MFM currently has ten direct EVM crates containing 25,113 physical Rust lines. A lexical inventory
found 337 top-level public declarations/re-exports and 286 public inherent methods, before counting
the public handles and registry functions generated by macros. The subsystem is not large because
the active product needs a broad EVM platform. It is large because it combines:

- one production use: native and ERC-20 balances for `mfm.portfolio/snapshot@1`; and
- a speculative contract deploy/configure/validate platform with no production operation, setup
  kind, app registration, CLI route, or REST route.

The contract model, contract states, contract adapter, and EVM signing bridge form an 11,918-line
island with no production root. `mfm-evm-signing` also has a reverse edge from the otherwise
unconsumed `mfm-signers-keystore`; that does not create a product owner. With the 1,407-line contract
integration graph, the island accounts for 13,325 lines of direct crate and integration-test code. The
contract model/state/adapter portion alone contains 10,317 non-test-named lines and 109 lexical
top-level public declarations. This is not reusable infrastructure waiting for a caller. It is an
unowned product vertical slice whose abstractions, capability surface, transaction machinery,
runtime routing, documentation, and tests impose costs on the real portfolio path.

The active collector is also over-modeled. One EVM network expands into nine state kinds, three
internal operations, method-specific capability traits, method-specific evidence mirrors, custom
live runners, custom replay runners, an app provider proxy, three routing registries, nested receipt
families, and a fact-index query that reads facts the same run just wrote.

The architectural outcome should be:

- delete the contract lifecycle vertical slice;
- delete the grab-bag EVM core and use canonical Alloy primitives or small private codecs;
- retain only a small EVM read-capability contract and a small source-bound JSON-RPC transport;
- move the current balance collection semantics into the portfolio state/adapter vertical slice,
  where their actual domain ownership already lies;
- reduce each EVM network to one read state and one atomic fact-publication state;
- make live and replay use one state-owned deterministic reducer;
- delete EVM signer/runtime machinery without a production owner; and
- delete the CLI transaction-signing utility unless it is explicitly reaffirmed as product scope.

This reduces the current ten EVM crates to two for the current product:
`mfm-evm-capabilities` and `mfm-transports-evm`. A third narrow Alloy-backed transaction crate is
allowed only if `keystore tx-sign` is deliberately retained.

## Root causes

### 1. Speculative generality became permanent surface

Contract lifecycle, mutation, signer routing, logs, nonce recovery, ABI assertions, and finality were
built without a product entry point. Tests then made the speculative shapes feel mandatory. This
created public types and design commitments before real callers could establish the minimal useful
abstraction.

### 2. State execution is nominal while adapters own the real behavior

`ReadState::run` and `SideEffectState::submit` receive capability marker tuples, not provider values
(`crates/kernel/program/src/lib.rs:864-876,918-956`). EVM states therefore implement required methods
that unconditionally return “adapter required”. Examples include:

- joint tip and native balance in
  `crates/states/evm/src/native_balance_collect.rs:338-353,634-654`;
- ERC-20 metadata and balance in
  `crates/states/evm/src/erc20_balance_collect.rs:379-392,594-607`; and
- contract mutation/validation in `crates/states/evm-contracts/src/mutations.rs:79-87,208-216`
  and `validation.rs:315-325`.

The adapter is consequently the real state implementation. It reloads state config and inputs,
constructs RPC requests, sequences calls, materializes outputs, records a second evidence model, and
implements replay separately. MFM therefore has two state execution contracts: one public contract
that cannot execute and one adapter-specific contract that can.

### 3. Every layer creates another vocabulary

Addresses, networks, chain ids, selectors, hashes, quantities, transaction styles, source evidence,
artifacts, observations, facts, and receipts are repeatedly wrapped and converted. Capability DTOs
are not directly retained, so adapters stringify typed values into custom evidence and replay parses
them back. A single read semantic change can touch capability, state, adapter live path, evidence
schema, replay decoder, app wrapper, operation exports, portfolio hydration, and source-text boundary
tests.

### 4. Internal topology was promoted to public domain schema

Joint tips, per-resource observations, record states, batch receipts, network receipts, zero-or-one
vectors, `*_required` booleans, fixed coverage strings, fixed source-read counts, and three internal
operations are all public typed surfaces. They mostly prove graph shape that typed handles and the
certified spec already prove.

### 5. Routing tries to be both fallback and source pinning

Runtime config and transport model sources, policies, preferred sources, ordered fallback, routes,
and registries. Each method nevertheless reselects and reprobes a source, while downstream state
rejects any change in source identity. This produces complexity without coherent failover.

## Delete the contract lifecycle vertical slice

This is the highest-confidence removal. Delete, together:

- `crates/evm-contract-model/`;
- `crates/states/evm-contracts/`;
- `crates/adapters/evm-contracts/`;
- `tests/integration/tests/contract_state_graph.rs`;
- `docs/evm-contract-states.md`;
- contract lifecycle sections in `docs/evm-rpc-routing.md`,
  `docs/persisted-public-surfaces.md`, CLI/REST/app docs, and design/architecture docs;
- contract model/state/adapter dependencies from the workspace and integration-test manifest;
- contract typestate compile-fail tests and contract adapter fixtures;
- historical contract setup-kind tombstone assertions in
  `crates/app/src/config_setup.rs:331-347`;
- historical missing-package assertions for old contract config/op crates once the generic metadata
  contract is sufficient;
- contract-only capability types and implementations;
- contract-only transport methods;
- contract-only signer/runtime-config wiring; and
- all contract schema descriptors, adapter identities, replay registrations, examples, and
  re-exports.

No contract facade, “experimental” feature, deprecated module, or disabled registration remains.
If a certified contract objective is approved later, it starts from its actual requirements and the
kernel side-effect contract. Git history can supply useful algorithms, but not architectural
authority.

### Defects inside the contract island reinforce deletion

These are not a retention checklist. They explain why moving or renaming the current code is unsafe.

1. **General ABI claims are false.** The ABI model drops tuple components and event indexing,
   lacks tuple/array support, and then adds another contract-model facade.
2. **Integer decode is wrong.** `evm-core/src/abi.rs:690-695` decodes every signed/unsigned integer
   from only the low 64 bits and ignores signed two's-complement semantics, while the contract model
   claims `uint256` support (`evm-contract-model/src/abi.rs:109-129`).
3. **ABI canonicality is not enforced.** Boolean `2` becomes false, address left padding is not
   validated, extra trailing static bytes can be accepted, decimal integer inputs are host-width,
   and event overload lookup takes the first matching name.
4. **Validation reads are unanchored.** Contract call assertions use `Latest`
   (`adapters/evm-contracts/src/read_validation.rs:181-211`) even though configured instances carry
   a confirmed anchor.
5. **Advertised selectors are unsupported.** The public contract model accepts safe/finalized tags,
   but adapter conversion rejects them (`mutation_support.rs:748-770`).
6. **Signing happens twice.** Preparation signs to obtain an expected transaction hash and
   submission signs again (`adapters/evm-contracts/src/lib.rs:585-631,913-969`). The generic signer
   contract does not guarantee deterministic signatures; remote or hardware signers can prompt
   twice or produce a different valid signature.
7. **One side-effect node can submit multiple transactions.** Configure loops over prepared
   transactions. A later failure can follow already-live earlier mutations, violating the clean
   one-node/one-mutation reasoning model.
8. **Empty configure is represented as a zero-transaction side effect.** No mutation should mean no
   side-effect node, not a special empty path.
9. **Nonce semantics disagree.** Preparation reads `Latest`; recovery uses `Pending`. This is not a
   safe nonce reservation contract.
10. **Preparation read provenance is discarded.** Nonce, fee, and gas responses are not coherently
    checked against one binding and their raw evidence is lost.
11. **The source validator does not validate one source.** It checks network/chain and non-empty
    source strings rather than source coherence.
12. **Receipt evidence is dropped.** The adapter constructs receipts with `receipt_evidence: None`.
13. **Finality is not replay-provable.** Live canonical/latest reads collapse into a confirmation
    count; replay only checks that the stored number exceeds the depth.
14. **Call and log evidence is derived duplication, not replay authority.** Raw return bytes/logs
    needed to recompute validation are not retained consistently.
15. **Nonce occupancy cannot prove non-submission.** It scans only latest and pending full blocks,
    usually yielding `Unknown` (`transports/evm/src/lib.rs:450-500`).
16. **Polling mechanics leak into semantic prepared authority.** `poll_interval_ms` and
    `max_receipt_polls` are operational scheduling details, not mutation identity.
17. **Provider layering is excessive.** Eleven provider traits, eight-plus-four trait-object bundles,
    runtime wrappers, factories, callbacks, phase plans, and separate replay reconstruction exist
    without a production implementation.
18. **Transaction values and fees are narrowed to `u128`.** EVM quantities are 256-bit.
19. **Contract JSON wrappers store canonical JSON inside JSON strings.** `AbiJson`, `BytecodeJson`,
    `AbiArgumentValue`, and `ExpectedValue` serialize as `{ "json_text": "..." }`, creating
    parse/string/parse cycles instead of a typed ABI model.
20. **Contract scalars duplicate kernel authority.** The 740-line scalar module wraps network,
    artifact, schema, semantic, evidence, digest, address, code-hash, and block-hash identities, then
    reparses generic kernel identifiers on access.
21. **Speculative fields have no behavior.** `ArtifactPort`, chain fingerprint, finality/observation
    policy, interface digest, creation-bytecode digest, selector/event-policy digest, and several
    profile digests are declarations, fixtures, or deserialization only.
22. **Reports duplicate derivable truth.** Validation reports retain results and evidence containing
    the same results, plus `passed`/`valid` booleans derivable from entries.
23. **Documentation overstates the implementation.** `docs/evm-contract-states.md` and
    `docs/persisted-public-surfaces.md` claim replayable finality, receipt, call/log, and
    not-submitted proof authority that the retained evidence does not provide.

## Delete the mixed `evm-core` abstraction

`mfm-evm-core` is not one stable abstraction. It combines:

- a partial dynamic ABI parser/encoder (about 699 lines);
- ERC-20 word and call encoding;
- address normalization;
- generic hex parsing/formatting;
- quantity parsing and formatting;
- custom RLP (about 120 lines);
- custom legacy and EIP-1559 transaction envelopes (about 297 lines); and
- a dynamic `UtilError { code, String }` error convention.

The modules have different owners and change reasons. Their common property is only “related to
EVM”. This makes portfolio address validation depend on an ABI/RLP/transaction crate and makes the
transport depend on transaction parsing helpers.

Delete the crate after moving only active responsibilities to their true owners:

- use Alloy `Address`, `B256`, and `U256` internally;
- keep persisted portfolio address normalization in the portfolio model, with one strict canonical
  serialization;
- use typed Solidity calls for `decimals()` and `balanceOf(address)`, or keep a tiny private codec
  beside the portfolio EVM collector;
- keep JSON-RPC quantity parsing private to the transport;
- use maintained Alloy consensus/envelope/RLP types if transaction signing survives; and
- use typed boundary errors rather than propagating generic string codes through layers.

Delete currently unused public helpers such as `format_u256_units`, `parse_u8_u256`,
`normalize_nonempty_hex_str`, `validate_raw_transaction_hex`, and
`normalize_evm_address_native_balance_fact`. Make any surviving local helpers private.

Specific correctness reasons to remove the custom implementations include:

- `LegacyTxToSign` and `Eip1559TxToSign` use `u128` for value and fees;
- `normalize_hex_str` pads odd-width input, so address paths can disagree on whether a 39-digit
  payload is accepted;
- ABI decimal integers are host-width while advertised Solidity widths extend to 256 bits;
- `WeiAmount` can preserve different authored spellings for the same semantic value, producing
  different content hashes; and
- maintaining manual ABI, RLP, transaction, and JSON-RPC encoding multiplies protocol-correctness
  surface without a product requirement for a general client.

## Delete or isolate transaction signing

The contract path contains overlapping transaction representations:

- `LegacyTxToSign` and `Eip1559TxToSign`;
- `evm_signing::EvmTransactionStyle`;
- contract `EvmTransactionStyle` and `EvmTransactionPolicy`;
- `PreparedContractTransactionStyle` and prepared evidence;
- `TransientRawTransaction`; and
- capability `SignedEvmPayload`.

Deleting the contract island removes all of them except the CLI's independent path. The documented
`keystore tx-sign` command (`bin/cli/src/commands/keystore/tx_sign.rs` and
`bin/cli/src/support/keystore.rs:371-425`) directly constructs and signs an EIP-1559 transaction in
binary support code. It does not use `mfm-evm-signing` or `mfm-signers-keystore`, and it violates the
thin-binary boundary.

The recommended decision is to delete `keystore tx-sign`, its parity tests, help text, and README
contract. It is not part of the sole MFM objective and is the only reason to retain general
transaction-envelope code.

If product ownership explicitly reaffirms the command before its deletion commit, the only accepted
alternative is one narrow Alloy-backed library surface that:

- uses `U256` protocol quantities;
- constructs the typed transaction envelope;
- exposes a digest-only signing request;
- finalizes one signed envelope;
- never persists raw signed transactions or secret material; and
- is invoked through an app/service boundary so the CLI remains transport-only.

That alternative replaces and deletes `evm-core` and `evm-signing`; it does not preserve either
crate, add adapters for their types, or share the abandoned contract transaction model.

## Delete orphan signer infrastructure

After contract deletion:

- `mfm-evm-signing` is unnecessary;
- `crates/signers/keystore` has no package consumer;
- runtime `[signers]` configuration is parsed and tested but not used by app assembly;
- `RuntimeConfigRequirement::evm_with_signers` has no production caller;
- `mfm-app` declares an unused `mfm-signing` dependency; and
- the generic `mfm-signing` crate has no remaining consumer outside those deletion-bound surfaces.

Delete `mfm-evm-signing`, `mfm-signers-keystore`, runtime signer parsing/accessors/errors/tests/docs,
`mfm-signing`, and their dependency edges. Cargo metadata and source search show that every
`mfm-signing` consumer is in the contract/signing/runtime surfaces being deleted or is the already
unused app dependency. Preserve `[keystores]` only because CLI key administration uses it.

The current generic keystore signer also imports EVM signing identity constants. A generic signer
provider must not change for each protocol-specific purpose. If generic signing is reintroduced in a
future owned feature, the caller owns purpose/domain policy and the provider owns only key identity,
algorithm enforcement, secret handling, and signing.

## Collapse the capability surface

`crates/evm-capabilities/src/lib.rs:75-297` defines twelve marker types and twelve one-method provider
traits, followed by twelve request/response families:

1. chain identity;
2. block read;
3. balance read;
4. call read;
5. code read;
6. logs read;
7. nonce read;
8. fee read;
9. gas estimate;
10. transaction submit;
11. receipt read; and
12. nonce occupancy read.

Production portfolio collection uses only block, balance, and call. Delete chain identity as a
state-facing capability; it is a transport session-binding check. Delete code, logs, nonce, fee,
gas, submit, receipt, and occupancy until a production vertical slice needs them.

The retained crate should contain only:

- three certification markers for least-authority accounting: block, balance, and call;
- one small `EvmReadSession` provider trait implementing those operations;
- checked request/result types using Alloy primitives;
- one exact block selector/anchor vocabulary;
- one serializable redacted session-evidence type; and
- one closed redacted error contract.

Do not retain a provider trait per method, an aggregate supertrait, a factory trait, a bound-provider
trait, and an app proxy. Marker granularity can express certified authority without multiplying live
provider abstractions.

Use existing checked MFM identifiers where their grammar is sufficient. Do not keep separate
portfolio, capability, contract, runtime, transport, and string wrappers for the same semantic
network/source concept.

## Replace routing with one source-bound session

EVM routing is modeled at least three times:

- raw and checked runtime config (`crates/runtime-config/src/raw.rs` and `src/evm.rs`);
- public transport `EvmRuntimeSource`, `EvmSourcePolicy`, `EvmSourceRegistry`, `EvmRoute`, and
  `EvmRouteRegistry` (`crates/transports/evm/src/registry.rs`); and
- app conversion of every field (`crates/app/src/live_transports.rs:187-234`).

A route carries both `source_ref` and `policy_id`; the policy already carries ordered sources.
Candidate construction rotates the policy around the preferred source. When policy is omitted,
runtime config synthesizes one (`runtime-config/src/evm.rs:267-287`). These are overlapping choices
and a hidden fallback path.

The supposedly bound provider is not bound. `bind_network` only stores the client and semantic
binding (`transports/evm/src/lib.rs:104-114`). Every method calls `verified_source` again
(`:503-544,766-869`), reprobes `eth_chainId`, and can choose another endpoint. Actual method failure
does not try the next source, chain mismatch returns immediately, and state later rejects source
drift. Ordered fallback and exact source equality therefore work against each other.

Choose the simpler model now:

```text
semantic network -> one source ref -> one secret-bearing endpoint

async bind(network, expected_chain)
  -> resolve the one source
  -> construct the client fallibly
  -> probe eth_chainId once
  -> return EvmReadSession { private endpoint, checked binding, redacted audit evidence }
```

Every read in a network collection uses that exact session. Delete source policies, policy ids,
preferred-source rotation, synthesized policies, fallback candidates, public transport registries,
per-method source verification, and app model-to-model mapping. If source failover is needed later,
it must retry the whole logical observation against a newly bound session; it must not drift sources
mid-observation.

Runtime-local source identity is audit provenance, not holding domain equality. Retain it once in
the collection evidence, not in joint tip, metadata, each read response, each fact, each receipt
entry, each batch receipt, and the network receipt. If source identity ever becomes semantic trust
authority, it must be a certified named oracle in semantic config rather than a process-local route
id.

Runtime config loading must also be capability-specific. An EVM read run validates EVM read routes;
malformed unused signer or keystore sections must not block it.

## Shrink and harden the JSON-RPC transport

After contract deletion, retain only the RPC methods required by portfolio balances:

- `eth_chainId` during session binding;
- `eth_getBlockByNumber` / `eth_getBlockByHash` for anchor resolution and identity reads;
- `eth_getBalance`; and
- `eth_call` for typed ERC-20 `decimals()` and `balanceOf(address)`.

Delete `web3_clientVersion`, code/log/nonce/fee/gas/submission/receipt/occupancy implementations and
their tests. Client version is best-effort and non-authoritative
(`transports/evm/src/lib.rs:116-131`); it should not be persisted or replaced with `"unknown"`.

For retained RPC calls:

- make client construction return `Result`; delete the `unwrap_or_else(Client::new)` fallback at
  `transports/evm/src/lib.rs:78-83`;
- set explicit connect/request timeouts and a bounded response-body size;
- validate the JSON-RPC version and response id, not only the `result`/`error` shape;
- reject malformed quantity, hash, address, or response fields; do not coerce them to false/none;
- use protocol-width types and checked arithmetic;
- preserve only reviewed, redacted diagnostics;
- issue exact EIP-1898 hash selectors with `requireCanonical` for anchored state reads; and
- after all balance calls, read the anchor **by number** and require its returned canonical hash to
  equal the original anchor hash before publication.

An `eth_getBlockByHash` re-read alone is not a canonicality proof because an orphaned block can still
be retrievable by hash. The final number-to-hash comparison is required in addition to the
`requireCanonical` state reads.

Current defects in methods that should be deleted include fee-call failures being converted to
optional absence, saturating `base_fee * 2 + priority`, missing receipt status becoming false, logs
omitting `blockHash`/`removed`, and nonce occupancy silently skipping malformed transaction fields.
They are evidence that unused generic method coverage is a liability.

## Collapse the portfolio EVM graph

Let:

- `N` be the number of native accounts;
- `M` be the number of ERC-20 account/token balance pairs; and
- `U` be the number of unique ERC-20 contracts.

The current EVM graph creates:

```text
2 + 2N + U + 2M + [N > 0] + [M > 0]
```

nodes per network: one joint-tip state, one network receipt, observe/record pairs, token metadata
states, and optional family batch receipts. This excludes the later portfolio receipt, fact-index
read, hydration, selection, snapshot, and report nodes.

Without endpoint fallback, the current transport performs approximately:

```text
2 + 4(N + U + M)
```

HTTP requests because every semantic block/balance/call read is preceded by another chain-id probe,
and every observation rechecks its block. A source-bound batch can perform:

```text
3 + N + U + M
```

requests: one chain probe, one latest block, all deduplicated reads at the exact hash, and one final
anchor-number read whose returned canonical hash must match.

### Delete the nine-state receipt pyramid

The current state kinds are:

1. resolve joint tip;
2. observe native balance;
3. record native fact;
4. assemble native batch receipt;
5. observe ERC-20 metadata;
6. observe ERC-20 balance;
7. record ERC-20 fact;
8. assemble ERC-20 batch receipt; and
9. assemble EVM network receipt.

Delete their public empty configs, input wrappers, observation wrappers, source keys, family receipt
entries, batch receipts, network receipt, helper exports, and registry enumeration.

Receipt entries currently embed the full verified fact and repeat source key, block number/hash,
fixed coverage/status, and fact identity
(`native_balance_collect.rs:788-940`; `erc20_balance_collect.rs:732-875`). Batch receipts repeat
network/chain/anchor/source/count and entries. The network receipt repeats the anchor and embeds both
batches. Portfolio converts them into another receipt (`ops/portfolio-snapshot-op/src/lib.rs:191-241`).
Counts equal `entries.len()` and statuses are fixed. None of this should survive.

Delete public fields that pretend implementation constants are caller policy:

- `max_source_reads`, whose validators require exact hard-coded constants;
- `source_read_count`, which repeats those constants;
- configurable native coverage, which must equal one fixed string;
- fixed ERC-20 coverage/status strings;
- `successful_observation_count`, derivable from entries;
- `native_balance_required` / `erc20_balance_required` booleans;
- zero-or-one receipt vectors representing the same optionality; and
- empty `{}` config/input types. Add kernel support for `()` as config where needed.

Enforce real hard bounds once in portfolio config validation and bounded concurrency once in adapter
execution. The current portfolio model appears not to cap wallet/symbol/holding counts; adding such
bounds is meaningful, unlike serializing per-state constants.

### Use one fact algebra

Replace separate native and ERC-20 fact families with one portfolio-owned fact descriptor, for
example:

```text
EvmBalanceSnapshotFact {
  subject: {
    network,
    chain_id,
    account,
    asset: Native | Erc20 { contract }
  },
  anchor: { block_number, block_hash },
  raw_units: canonical U256 decimal string,
  decimals
}
```

Coverage and success status are implicit in the presence of a checked fact for every demanded
source. The network config owns native decimals. ERC-20 decimals are deduplicated internal read
material, not a public reusable state/output family. Store quantities canonically without floats.

### Replace the graph with two states per network

```text
CollectEvmNetworkState          ReadExternal
  -> PublishEvmHoldingsState    ManagedPlatformWrite
  -> EvmNetworkSnapshot handle
  -> portfolio pure assembly
```

`CollectEvmNetworkState` owns a deterministic request plan and reducer. It:

- accepts one checked EVM network and one sorted, unique source algebra;
- declares one checked session binding, which the adapter resolves to one `EvmReadSession`;
- resolves one latest anchor;
- deduplicates token metadata by contract;
- reads every native/token balance at the exact block hash;
- reads the anchor number after all observations and rejects it unless its current canonical hash
  equals the original anchor hash;
- returns one sorted canonical observation batch; and
- retains one external-read evidence batch sufficient for replay.

`PublishEvmHoldingsState`:

- validates the batch;
- records every fact in one managed-write attempt;
- returns one direct, sorted `EvmNetworkSnapshot`; and
- relies on one store attempt commit to atomically publish all facts and the output.

`RunnerOutputBuilder::record_fact` already permits multiple facts and state specs already allow
multiple emitted fact descriptors. The read/write effect boundary remains intact; network IO and
fact persistence are not combined in one state.

Batching changes retry granularity from a holding to a network. Under this refactor's explicit
priority, the node/type/code-path reduction is worth that trade. If measurement later proves that
per-holding retry is necessary, individual read/write pairs may return, but receipt layers,
same-run fact queries, method-specific replay branches, and duplicated fact families still must not.

### Delete same-run fact selection and hydration

The portfolio adapter queries the fact projection for facts the same graph just recorded, then reads
their artifacts and reconstructs native/ERC-20 fact objects
(`crates/adapters/portfolio/src/selection.rs:110-176,257-398,400-512`). Typed producer handles and
committed state output already prove exact lineage and completion.

Consume the direct `EvmNetworkSnapshot` handle in portfolio assembly. Continue recording facts for
durable external use, but do not round-trip through the fact index to move data between nodes in the
same certified graph. Delete EVM-specific query-plan helpers currently misplaced in
`mfm-states-evm`, native/ERC-20 hydration branches, EVM receipt-pinned selection code, and the EVM
portion of the app's custom portfolio replay fan-in.

This is a deliberate update to the receipt-as-authority decision in
`docs/design.md:193-201` and `docs/architecture.md:147-157`; those documents must change in the same
commit as the code. The direct typed output and retained state evidence become authority instead.

## Put portfolio semantics in the portfolio vertical slice

After graph collapse, move:

- EVM balance source/fact/snapshot types and the two state contracts into `mfm-state-portfolio`;
- their live/replay runner binding into `mfm-adapters-portfolio`; and
- private per-network expansion into `mfm-op-portfolio-snapshot`.

Then delete:

- `crates/states/evm/`;
- `crates/adapters/evm/`;
- `crates/ops/evm-collectors-op/`;
- their Cargo edges and registry functions;
- their broad public re-exports; and
- app lists that manually enumerate the nine old state keys.

This is not “put EVM everywhere in portfolio”. Reusable protocol authority remains in
`mfm-evm-capabilities`, and reusable live protocol implementation remains in
`mfm-transports-evm`. The current domain action—collect the portfolio's configured holdings—is owned
by portfolio. A future second consumer can justify a reusable EVM state family based on two concrete
uses rather than preserving today's portfolio-coupled crate under a generic name.

Do not merge adapter and transport merely to reduce crate count. The adapter binds state intent,
evidence, and replay; the transport owns HTTP/JSON-RPC. That is a real architecture boundary with
different authority and test requirements.

## Replace app and adapter indirection

`mfm-adapters-evm` currently defines `EvmProviderFactory`, `EvmBoundProvider`, and
`EvmRunnerCapabilities` (`adapters/evm/src/lib.rs:302-356`). App implements the factory and adds
`BoundLiveEvmProvider`, whose three methods only forward to the transport
(`app/src/evm_collector.rs:21-70`). The transport already implements the capability traits.

Delete the forwarding provider, aggregate supertrait, and duplicate factories. App assembly should:

1. load only the required runtime config family;
2. construct the transport resource;
3. register one portfolio EVM collection runner factory; and
4. let that factory asynchronously bind one source session for each network attempt.

Transport/backend implementation identity belongs to the provider implementation, not to each
consumer adapter. Delete contract-vs-collector special cases that assign different implementation
ids to the same RPC authority.

App certification should call one portfolio registration function rather than separately register
EVM op descriptors, state descriptors, two fact families, replay state-key lists, and forwarding
providers.

## Make live and replay one semantic path

The collector adapter has separate evidence DTOs for joint tip, native balance, canonical selector,
ERC-20 call, and source conversion (`adapters/evm/src/lib.rs:68-290`). They stringify addresses,
hashes, calldata, return bytes, and quantities. Replay parses those strings back into capability DTOs
and manually repeats the live validation path (`:969-1515`).

Replace this with the kernel/state contract:

```text
state.plan(config, input) -> checked deterministic read plan
adapter.execute(plan, EvmReadSession) -> canonical retained evidence
state.reduce(config, input, evidence) -> output
replay.decode(retained evidence) -> state.reduce(config, input, evidence)
```

One generic external-read runner should own config/input loading, evidence recording, output
comparison, and live-vs-replay dispatch. The same reducer must reject tampered evidence in live
verification and replay. Delete:

- impossible `ReadState::run` and `SideEffectState::submit` implementations;
- “adapter required” runtime errors;
- adapter-specific copies of capability responses;
- string round trips for typed protocol values;
- separate live materialization helpers and replay reconstructions;
- callback/plan/phase abstractions that merely indirect direct logic; and
- app-owned replay of operation/state semantics.

This kernel change is cross-cutting and affects BTC/portfolio read states as well. It must be an
explicitly reviewed portion of the atomic EVM graph cutover, not an EVM-local workaround and not a
parallel trait left beside the old contract. If a shared managed fact-record runner genuinely
deletes duplicated implementations, place it in a shared fact adapter kit; do not create an
abstraction used by only one side.

## Canonical retained vocabulary

The retained design needs one representation per concept:

- semantic network: existing checked MFM/portfolio network identity plus non-zero chain id;
- in-memory address: Alloy `Address`;
- persisted portfolio address: one strict normalized lowercase value type;
- block hash and transaction hash: Alloy `B256` internally, one fixed-width canonical hex form at
  persisted boundaries;
- quantities: Alloy `U256` internally, canonical decimal strings in hashed JSON;
- anchor: one number/hash EVM variant, preferably the existing portfolio execution-anchor algebra;
- block selector: one capability-owned selector, including exact hash + `requireCanonical`;
- provenance: one serializable redacted session-evidence value; and
- asset source: one `Native | Erc20 { contract }` algebra.

Delete duplicate `EvmNetworkId`, `ContractAddress`, `EvmBlockHash`, `EvmCodeHash`, source binding,
validation source, transaction style, selector, quantity, and artifact-identity wrappers rather than
adding conversions among them.

At schema boundaries, deserialize once into checked types and serialize once canonically. Hashed
structures contain no floats. Provider endpoints, auth headers, client messages, paths, signer
material, signatures, and raw signed transactions never enter retained evidence or public errors.

## Target architecture

For the current product, the complete EVM shape is:

```text
mfm-op-portfolio-snapshot
  private EVM expansion
          |
          v
mfm-state-portfolio
  CollectEvmNetworkState --------------+
          |                             |
          | read plan / reducer         | retained canonical evidence
```

### Retained EVM-specific crates

`mfm-evm-capabilities` owns only transport-neutral read authority, checked requests/results,

No transaction crate exists by default. If and only if `keystore tx-sign` is affirmed, one narrow
Alloy-backed primitive owns transaction construction/digest/finalization. It does not own RPC,
workflow topology, signer resolution, contract lifecycle, or persistence.

## Definition of done

The refactor is complete only when all of the following are true:

- the current product has at most two EVM-specific crates, plus an explicitly owned optional
  transaction crate;
- Cargo metadata contains none of the eight deleted EVM packages;
- the contract lifecycle graph, schemas, docs, setup tombstones, and runtime signer routing are gone;
- only block, balance, and call remain as state-facing EVM read authority;
- one async bind creates one source-stable session per network attempt;
- no per-method `eth_chainId` probe, source policy, fallback rotation, or client-version call remains;
- every anchored state read uses EIP-1898 `requireCanonical`, followed by one anchor-number read
  whose returned canonical hash must equal the original anchor hash;
- one canonical address/hash/U256/anchor/provenance vocabulary is used;
- one unified EVM balance fact covers native and ERC-20 holdings;
- the EVM network graph has exactly one external-read state and one managed-write state;
- the managed-write attempt publishes the complete fact batch atomically;
- portfolio assembly consumes a direct typed network snapshot, not a same-run fact query;
- live and replay invoke the same deterministic reducer over the same canonical evidence;
- no required state method unconditionally returns an adapter-required error;
- app wiring constructs resources and registers one portfolio EVM runner family without a forwarding
  provider;
- no old alias, reader, migration, fallback, deprecated module, or feature-gated implementation
  remains;
- no endpoint, credential, signer material, signature, raw transaction, or provider message is
  persisted or publicly rendered;
- all hashed values are canonical, contain no floats, and use one semantic serialization;
- tampered/missing/reordered evidence, wrong chain, source setup failure, malformed RPC, and reorged
  anchor tests fail closed; and
- all focused Cargo checks, required Nix gates, and final CI pass.

## Invariants that simplification must not remove

Deletion is aggressive; correctness boundaries remain strict:

- append-only run streams and per-append atomicity;
- content-addressed manifests, facts, artifacts, snapshots, and outputs;
- canonical JCS-style JSON and no floats in hashed structures;
- no ambient IO in state logic;
- exact semantic network and non-zero chain identity;
- exact number/hash anchors, canonical hash selectors, and a final number-to-hash canonicality check;
- replay from retained evidence only, never live transport or signer access;
- atomic fact/output publication;
- deterministic ordering and exact coverage of configured holdings;
- explicit collection bounds and bounded concurrency;
- secret and bearer-material exclusion from events, facts, artifacts, errors, CLI, and REST;
- adapter/transport separation; and
- kernel side-effect ledger/saga/idempotency semantics if EVM mutation is ever reintroduced.

The objective is not to make these invariants optional. It is to have one implementation of each
invariant, in one obvious owner, on one production path.
